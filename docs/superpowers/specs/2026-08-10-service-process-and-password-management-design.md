# Yep Anywhere 跨平台服务进程与密码管理设计

- 日期：2026-08-10（第二阶段于 2026-08-12 简化修订）
- 状态：第一阶段已实施；第二阶段简化设计已确认，待书面审阅后更新实施计划
- 适用平台：Windows、macOS
- 设计原则：复用现有实现、最少改动、平台原生守护、前后端职责清晰

## 1. 背景

项目已经具备开发模式、生产 Bundle、macOS LaunchAgent、Windows PowerShell 和计划任务脚本，以及基于 `auth.json` 的登录密码功能。但现有能力存在以下缺口：

- Windows 下部分启动路径仍依赖当前终端，关闭终端后服务可能退出。
- Windows 计划任务未安装时不会开机或登录自启动，且人工启动与自启动存在不同生命周期路径。
- macOS 与 Windows 的服务管理命令、菜单和自启动语义不完全一致。
- 根目录 `yep.mjs` 同时承担系统选择、菜单和部分业务逻辑，不符合“只做双端入口分发”的目标。
- 服务管理脚本的用户可见交互未完全中文化。
- 登录密码管理目前混在“本地访问”的网络设置提交中，缺少独立管理员密码验证。
- 现有 `auth.json` 解析失败时会静默回到认证关闭状态，存在配置损坏后意外放开访问的风险。
- 现有明文密码 CLI 参数和运行时认证绕过不适合作为个人项目的长期恢复机制。
- 管理员密码缺少一条跨开发、生产和自定义 Profile 通用的本机设置与恢复路径。

本设计补齐以上能力，同时保持未被本需求涉及的现有行为不变。

## 2. 目标

### 2.1 服务进程目标

1. 开发模式和生产模式均可后台静默运行，不受启动终端关闭影响。
2. Windows 与 macOS 均可启动、停止、重启开发和生产模式。
3. 生产模式可启用、关闭和查看登录桌面后的自动启动状态。
4. 生产模式可一键重新构建、重启并验证。
5. Windows 与 macOS 共用一个入口脚本，由入口自动识别系统并分发。
6. 服务脚本自身的菜单、提示、状态、帮助和错误均使用中文。
7. 开发模式与生产模式使用不同端口和数据 Profile，可以同时运行且互不误操作。

### 2.2 密码管理目标

1. 保留前端现有“设置 → 本地访问”中的认证区域，将它与网络设置拆成独立提交的密码管理卡片，不新增设置分类或路由。
2. 前端只管理普通登录密码；管理员密码只通过一条服务器本机命令设置或重置。
3. 普通登录密码只有“关闭”和“启用”两种状态；关闭时删除普通登录密码，重新启用时必须设置新密码。
4. 设置、修改和关闭普通登录密码必须从服务器本机的回环地址页面发起，并在每次操作时验证管理员密码。
5. 服务器本机登录页允许使用管理员密码登录，作为忘记普通登录密码时进入设置页的恢复路径；远程设备只能使用普通登录密码。
6. 同一操作系统用户运行的开发、生产和自定义 Profile 共用一个全局管理员密码。
7. 普通密码或管理员密码错误时必须有明确且不泄露凭据状态的提示。
8. 不增加登录失败次数限制、延迟、锁定、验证码、多用户或角色系统。
9. 所有普通登录密码状态变更必须清除当前 Profile 的已有登录会话。
10. 认证配置损坏或写入失败时必须安全失败，不得静默关闭认证或覆盖原文件。

## 3. 非目标

本次不包含：

- Windows Service 或 NSSM 等第三方服务包装器。
- 开发模式开机自启动。
- 系统启动后、用户登录前的系统级服务。本次 Windows 与现有 macOS 行为一致，采用用户登录后自动启动。
- Linux 服务管理能力扩展；保持项目现有 Linux 行为。
- 用户、角色、多管理员或权限分级系统。
- 前端管理员密码管理、管理员密码提示问题、邮件找回或网络恢复接口。
- 管理员密码明文、可逆密文或密码提示内容存储。
- 登录失败限制、验证码、账户锁定或登录退避策略。
- 独立“密码管理”设置分类、密码强度计或复杂密码策略。
- 直接 HTTPS、可信代理、Tailscale 或桌面内部通道上的远程管理员操作。
- 认证状态文件的跨进程运行期锁和 Windows ACL 重写框架。
- 按 Profile 配置不同管理员密码、遍历 Profile 或重置管理员密码时批量注销会话。
- 复杂生产版本回滚系统。
- 构建系统重写及无关代码重构。

## 4. 总体方案与取舍

### 4.1 采用混合式平台原生方案

采用以下职责划分：

```text
yep.mjs（统一入口，只识别系统和转发参数）
├─ Windows → scripts/yep.ps1 → PowerShell + Task Scheduler
└─ macOS   → yep.sh          → shell + launchd
```

选择理由：

- Node.js 适合提供稳定、跨平台的统一入口，但不重复实现系统服务管理。
- Windows PowerShell 能直接管理计划任务、进程、ACL 和隐藏窗口。
- macOS shell 能直接管理 launchd、进程、权限和日志。
- 生产服务交给操作系统原生管理器守护，比单纯 Node.js `detached` 子进程更容易查询、重启和自启动。
- 复用现有 `yep.mjs`、`scripts/yep.ps1`、计划任务脚本、`yep.sh` 和 LaunchAgent 脚本，避免引入新的服务框架。

未采用的方案：

- 全部使用 Node.js 管理进程：跨平台代码表面统一，但仍需分别对接 Task Scheduler 和 launchd，且 Windows 子进程、信号和进程树管理更容易产生边缘问题。
- Windows Service：可在登录前启动，但需要管理员权限、服务账户与额外安装/卸载模型，不符合当前用户级 macOS LaunchAgent 语义和最少改动要求。

### 4.2 子系统边界

- 统一入口只做平台分发，不包含菜单、端口、进程和认证逻辑。
- Windows PowerShell 和 macOS shell 各自负责本平台的菜单、命令和服务管理。
- 服务脚本只负责把 `setup-admin-password` 命令转交给同一个 Node 管理入口，不读取、校验或写入密码。
- 后端认证模块负责各 Profile 的 `auth.json`、普通登录密码、会话和 v1→v2 迁移。
- 独立的管理员密码服务按需读取当前系统用户唯一的 `~/.yep-anywhere/admin.json`，负责全局管理员哈希的设置和验证。
- 前端现有“本地访问”认证卡片只调用认证 API，不直接访问任何后端文件，也不持久化管理员密码。

## 5. 统一入口设计

### 5.1 入口职责

根目录 `yep.mjs` 只执行以下工作：

1. 读取 `process.platform`。
2. Windows 自动调用 `scripts/yep.ps1`。
3. macOS 自动调用 `yep.sh`。
4. 原样传递全部命令行参数。
5. 继承标准输入、输出和错误输出，保留交互菜单能力。
6. 将后端脚本退出码原样返回给调用者。
7. 对不支持的系统显示中文错误并返回非零退出码。

入口不再询问用户选择操作系统，也不维护独立菜单或平台命令映射。无参数运行时，入口分发到当前系统脚本，由该脚本显示中文菜单；带参数运行时直接执行相应命令。

项目现有 `pnpm yep` 等入口继续指向 `node yep.mjs`。

### 5.2 命令接口

为兼容人工操作和自动化，命令参数保留英文，用户可见名称和反馈使用中文：

| 命令 | 中文功能 |
| --- | --- |
| `start-dev` | 启动开发模式 |
| `stop-dev` | 停止开发模式 |
| `restart-dev` | 重启开发模式 |
| `start-prod` | 启动生产模式 |
| `stop-prod` | 停止生产模式 |
| `restart-prod` | 重启生产模式 |
| `stop` | 停止开发和生产模式 |
| `status` | 查看完整服务状态 |
| `rebuild` | 重构建并重启生产模式 |
| `enable-autostart` | 启用生产模式登录自启动 |
| `disable-autostart` | 关闭生产模式登录自启动 |
| `setup-admin-password` | 设置或重置当前系统用户的全局管理员密码 |
| `help` | 显示中文帮助 |

现有 macOS 专用命令如 `enable-launchd` 可作为兼容别名保留，但菜单和文档统一推荐跨平台命令。

可继续支持 `start-dev --fg` 作为显式前台开发方式；交互菜单与 `start-dev` 的默认行为始终是后台静默运行。

## 6. 服务状态模型与命令语义

开发运行、生产运行和生产自启动是三个相互独立的状态：

```text
开发模式：停止 / 运行
生产模式：停止 / 运行
生产自启动：关闭 / 启用 / 配置异常
```

状态独立意味着：

- 开发与生产可以同时运行。
- `stop-prod` 不改变自启动设置；若自启动仍启用，下次登录仍会启动生产服务。
- `disable-autostart` 不停止当前生产服务。
- `enable-autostart` 只配置下次登录启动，不隐式启动当前服务。
- `stop` 停止两种运行模式，但不改变自启动设置。
- `rebuild` 不影响开发模式或生产自启动设置。

### 6.1 幂等要求

- 已运行时再次启动：提示“服务已在运行”，不创建重复进程。
- 已停止时再次停止：提示“服务当前未运行”，命令正常结束。
- 已启用时再次启用自启动：检查并修复配置，不重复注册。
- 已关闭时再次关闭自启动：提示当前已经关闭。
- 重启等价于准确停止目标模式后再启动该模式。

### 6.2 状态输出

`status` 至少显示：

- 当前操作系统和服务管理器。
- 开发模式：运行状态、端口、PID、数据 Profile、日志路径。
- 生产模式：运行状态、端口、PID 或系统任务状态、数据 Profile、日志路径。
- 生产自启动：已启用、已关闭或配置异常。
- 计划任务或 LaunchAgent 的安装、加载、运行和最近结果。
- 发现端口占用、残留 PID 或管理器状态不一致时给出中文诊断。

## 7. Windows 设计

### 7.1 平台基线

- 兼容系统自带 Windows PowerShell 5.1，不强制要求 `pwsh`。
- 生产服务由 Task Scheduler 管理。
- 开发服务由独立隐藏 PowerShell 启动器管理。
- 所有工作目录、脚本路径、Node 路径和日志路径使用绝对路径。

### 7.2 生产模式生命周期

计划任务是生产模式唯一的生命周期入口。人工启动、重启、重构建后的启动和登录自启动都通过同一个任务定义执行，避免产生两套不同的后台进程。

计划任务设计：

- 使用现有稳定任务名称 `YepAnywhereServer`。
- 以当前用户身份运行，不保存用户密码，不要求管理员权限。
- 触发器为当前用户 `AtLogOn`，与 macOS LaunchAgent 的登录后启动语义一致。
- 隐藏运行 PowerShell 守护脚本，并重定向标准输出和错误输出。
- 禁止同一任务并行创建多个实例。
- 不设置执行时限。
- 关键进程失败时按合理间隔重新启动，并使用接近持续守护的高重试次数。

自启动状态与任务动作分离：

- 首次启动生产服务时可以按需创建可人工启动的任务定义。
- 启用自启动时，为任务启用或安装 `AtLogOn` 触发器。
- 关闭自启动时，只移除或禁用登录触发器，保留任务动作供人工启动。
- 关闭自启动不会停止当前任务实例。

现有 `scripts/install-task-scheduler.ps1`、`scripts/uninstall-task-scheduler.ps1` 和 `scripts/run-yepanywhere.ps1` 继续复用，但职责调整为上述语义。

### 7.3 生产守护脚本

`scripts/run-yepanywhere.ps1` 继续作为计划任务执行入口，负责：

1. 校验生产 Bundle 和运行依赖。
2. 设置生产环境变量、端口和数据目录。
3. 隐藏启动服务器及必要的桥接进程。
4. 将输出写入现有生产日志目录。
5. 等待并监控全部关键进程，而不只监控主服务器 PID。
6. 任一关键进程异常退出时清理同一生产实例的残留进程并以非零状态退出，让计划任务重新拉起完整实例。

正常执行 `stop-prod` 时先停止计划任务实例，再清理经身份确认的生产进程，防止守护策略立即重新启动服务。

### 7.4 开发模式后台运行

默认 `start-dev` 使用 `Start-Process` 创建独立于当前终端的隐藏 PowerShell 启动器。启动器设置明确的工作目录和开发 Profile，运行现有 `pnpm dev`，重定向输入输出，并记录父进程 PID 与日志位置。

关闭原终端后，隐藏启动器和开发进程树继续运行。开发模式不注册计划任务，也不承诺应用崩溃后的系统级自动重启；开发构建工具自身仍按现有方式管理其子进程。

### 7.5 Windows 进程识别

停止服务不能仅按端口结束进程。目标身份至少综合：

- 计划任务运行状态。
- PID 文件或已知启动器 PID。
- 进程命令行中的项目路径、Bundle 路径、Profile 和模式。
- 对应端口作为辅助验证。

若端口属于无法确认的其他程序，脚本拒绝结束该程序，并显示端口、PID、进程名称和处理建议。

## 8. macOS 设计

### 8.1 生产模式

继续复用现有 launchd/LaunchAgent 方案：

- 当前用户登录桌面后由 LaunchAgent 启动生产服务。
- 使用 `RunAtLoad` 和 `KeepAlive` 保持生产服务常驻。
- 人工启动和重启也通过 launchd 管理的同一生产定义执行。
- `enable-autostart` 安装下一次登录所需的 LaunchAgent 配置，但不额外启动当前生产服务。
- `disable-autostart` 取消下一次登录自动加载，但不停止当前正在运行的生产服务。
- `stop-prod` 停止当前生产实例，但不删除自启动配置。

若需要在关闭自启动后人工运行生产服务，`yep.sh` 仍使用同一份生产 LaunchAgent 定义在当前登录会话中加载；下一次登录因未安装自启动项而不会自动加载。

### 8.2 开发模式

继续复用现有 `nohup` 后台启动方式，并确保：

- 标准输入连接 `/dev/null`。
- 标准输出和错误输出写入开发日志。
- 保存可验证的 PID。
- 关闭终端不会发送导致开发进程退出的信号。

### 8.3 脚本一致性

`yep.sh` 增加或补齐 `stop-dev`、`stop-prod`、`disable-autostart` 等与 Windows 一致的命令和中文交互，但不重写现有 launchd 安装和生产构建流程。

## 9. 重构建生产模式

`rebuild` 继续沿用项目当前的完整生产 Bundle 流程：

1. 执行 `pnpm lint`。
2. 执行 `pnpm typecheck`。
3. 构建客户端。
4. 执行 `pnpm build:bundle`。
5. 在 `dist/npm-package` 中使用 `npm ci --omit=dev` 安装运行依赖，不使用 pnpm。
6. 验证 Bundle 完整性。
7. 构建成功后通过当前系统的生产服务管理器重启或启动生产服务。
8. 比较运行服务、前端和 Bundle 的 `buildId`，确认部署的是本次构建。

错误语义：

- 构建或验证失败时，不继续执行生产重启。
- 不主动停止构建前正在运行的生产进程。
- 明确显示失败阶段、退出码和日志路径。
- 本次不增加生产版本快照和自动回滚机制。

## 10. 前端密码管理入口

### 10.1 复用现有设置位置

密码管理继续位于现有“设置 → 本地访问”页面，不新增设置分类、路由、布局或导航文案。现有认证表单从网络绑定、允许主机和本机开放等设置的一次性提交中拆出，成为同一页面内独立提交的认证卡片，避免管理员密码随无关网络设置一起发送。

远程访问该页面时，认证卡片只显示普通密码当前是否启用，以及“密码管理仅允许在服务器本机进行”的说明，不渲染可提交的管理员表单。前端依据状态接口返回的 `localManagementAllowed` 决定展示内容，但真正的访问控制始终由后端执行。

### 10.2 本机操作表单

普通登录密码只有“关闭”和“启用”两种状态：

- 关闭状态：显示“启用密码登录”，收集管理员密码、新普通密码和确认密码。
- 启用状态：显示“修改登录密码”和“关闭密码登录”两个独立操作。
- 修改：收集管理员密码、新普通密码和确认密码，不要求旧普通密码。
- 关闭：收集管理员密码，并要求一次明确确认；成功后删除普通密码。

每次操作都必须重新输入管理员密码。管理员密码只保存在当前表单组件的短生命周期 state 中；请求完成（无论成功或失败）、取消操作、离开页面或组件卸载时都清空。密码不得进入 URL、日志、错误遥测、`localStorage`、`sessionStorage`、IndexedDB 或其他持久化前端状态。

启用或修改成功后，后端清除当前 Profile 的全部会话，前端删除当前 Cookie 并进入登录页。关闭成功后同样清除会话和 Cookie，但由于普通密码认证已关闭，用户可以继续进入应用。

密码管理请求收到 `AUTH_ADMIN_NOT_CONFIGURED` 后，认证卡片显示唯一设置命令：

```bash
pnpm yep setup-admin-password
```

### 10.3 登录与忘记普通密码

远程登录页只接受普通登录密码。服务器本机通过回环 URL 打开登录页时，同一个密码框可输入普通登录密码或管理员密码；后端先验证普通密码，失败后才读取并验证全局管理员密码。

本机页面显示：“忘记登录密码时，可使用管理员密码登录后到设置中修改。”两种密码都失败时统一提示“登录密码或管理员密码错误”，不得指出管理员密码是否存在或哪一种校验失败。

管理员密码登录只创建现有类型的普通会话，不在 Cookie、浏览器状态或服务端 session 中记录“管理员身份”。该会话可以进入应用，但不能替代后续密码管理操作中的管理员密码再次确认。

## 11. 认证状态与存储模型

### 11.1 每个 Profile 的 `auth.json` v2

开发、生产和自定义 Profile 继续各自使用数据目录中的 `auth.json`，只保存该 Profile 的普通登录密码、本机开放开关和会话：

```json
{
  "version": 2,
  "localhostOpen": false,
  "account": {
    "passwordHash": "bcrypt hash",
    "createdAt": "ISO timestamp"
  },
  "sessions": {}
}
```

`account` 存在即表示普通密码登录已启用；`account` 不存在即表示关闭。不再保留独立 `enabled` 字段，也不存在“保存了密码但认证关闭”的第三种状态。关闭普通密码登录时删除 `account`，重新启用必须设置新密码。

普通密码沿用 bcrypt 成本参数 12。API 永远不返回哈希。

### 11.2 当前系统用户的全局 `admin.json`

同一操作系统用户运行的所有 Yep Anywhere Profile 共用：

```json
{
  "version": 1,
  "passwordHash": "bcrypt hash"
}
```

固定路径为 `~/.yep-anywhere/admin.json`，不受 `YEP_ANYWHERE_PROFILE` 或 `YEP_ANYWHERE_DATA_DIR` 影响。它只保存全局管理员密码的 bcrypt 哈希，成本参数同样为 12。各 Profile 的 `auth.json` 不包含管理员字段。

服务每次需要管理员验证时按需读取全局文件，因此管理员密码设置或重置后立即对开发、生产和自定义 Profile 生效，不需要停止或重启服务。设置或重置管理员密码不遍历 Profile，也不清除各 Profile 已有会话；已有会话仍不能代替管理员密码确认。

### 11.3 状态迁移

| 操作 | 普通密码状态 | `account` | 当前 Profile 会话 | 前端结果 |
| --- | --- | --- | --- | --- |
| 设置并启用 | 启用 | 新建 | 全部清除 | 清除 Cookie 并进入登录页 |
| 修改 | 启用 | 替换 | 全部清除 | 清除 Cookie 并进入登录页 |
| 关闭 | 关闭 | 删除 | 全部清除 | 清除 Cookie，可继续进入应用 |
| 设置或重置管理员密码 | 不变 | 不变 | 不变 | 命令完成后退出 |

前三种操作都必须从本机发起并临时验证管理员密码。现有登录会话不能替代管理员验证。

### 11.4 v1 迁移

读取现有 v1 `auth.json` 时自动迁移：

- `enabled === true` 且 `account` 有效：保留普通密码、`localhostOpen` 和 sessions，转换为 v2。
- `enabled !== true`：删除旧 `account`，保留 `localhostOpen`；sessions 清空，因为关闭状态不需要登录会话。
- 全局管理员密码不会由旧数据自动生成，也不会从普通密码复制。
- 管理员密码尚未设置时，旧用户仍可用保留的普通密码登录，但所有密码管理操作返回 `AUTH_ADMIN_NOT_CONFIGURED`。

迁移在内存中完成并通过原子写入落盘。旧文件解析失败、版本不支持或结构无效时不得迁移、覆盖原文件或回到认证关闭状态。

不存在 `auth.json` 表示全新 Profile，按 v2 的普通密码关闭状态初始化；不存在 `admin.json` 表示全局管理员密码尚未配置。这两种预期状态不属于配置损坏。

## 12. 密码 API 设计

继续复用现有 `/api/auth` 路由和认证服务，只调整请求验证与状态转换：

| API | 权限与用途 |
| --- | --- |
| `GET /api/auth/status` | 返回普通密码是否启用、当前会话是否有效和 `localManagementAllowed`；不返回管理员配置状态或任何哈希 |
| `POST /api/auth/enable` | 仅本机；管理员密码 + 新普通密码，设置并启用 |
| `POST /api/auth/disable` | 仅本机；验证管理员密码后关闭并删除普通密码 |
| `POST /api/auth/change-password` | 仅本机；管理员密码 + 新普通密码，替换已启用的普通密码 |
| `POST /api/auth/login` | 远程只验证普通密码；本机在普通密码失败后再验证管理员密码；成功后建立相同类型的普通会话 |
| `POST /api/auth/logout` | 注销当前登录会话 |

删除已废弃的 `POST /api/auth/setup`，不保留没有管理员验证的兼容写入口。删除旧 `--setup-auth`、`--auth-disable` 和 `AUTH_DISABLED` 运行时绕过；任何网络或本机命令都不能绕过上述管理员验证和状态转换。

### 12.1 本机请求判定

只有同时满足以下条件才是本机管理请求：

- 通过 `@hono/node-server/conninfo` 获得的真实 socket 对端地址为 `127.0.0.1`、`::1` 或 IPv4 映射的回环地址。
- 请求 URL 的主机为 `localhost`、`127.0.0.1` 或 `[::1]`。

不得用 `Host` 头单独判断，也不信任 `X-Forwarded-For`、`X-Forwarded-Proto` 等代理头。通过局域网 IP、Tailscale、反向代理或直接 HTTPS 访问都不能执行管理员操作或使用管理员密码登录。

真实 socket 地址只能识别 Node 直接连接的对端。如果同机反向代理主动把远程请求转发到回环地址并把 URL 主机改写为回环主机，Node 无法再辨别原始客户端；部署文档必须要求代理保留外部 Host，且不得将密码管理请求改写成回环请求。这是轻量个人部署方案的明确边界，本阶段不增加可信代理协议或额外管理端口来消除此限制。

`localManagementAllowed` 只用于前端呈现，不能作为后端授权输入。

### 12.2 稳定错误码

后端只保留密码管理所需的六类稳定错误码：

| 错误码 | HTTP | 含义 |
| --- | --- | --- |
| `AUTH_ADMIN_NOT_CONFIGURED` | 409 | 尚未设置全局管理员密码 |
| `AUTH_ADMIN_INVALID` | 401 | 管理员密码错误 |
| `AUTH_LOGIN_INVALID` | 401 | 普通登录密码错误；本机双路径登录失败（包括全局管理员文件不存在）时使用不区分凭据种类的安全文案 |
| `AUTH_LOCAL_REQUIRED` | 403 | 该操作只允许服务器本机回环访问 |
| `AUTH_PASSWORD_INVALID` | 400 | 密码缺失、类型错误、少于 6 个字符或确认不一致 |
| `AUTH_CONFIG_ERROR` | 500 | `admin.json`/`auth.json` 损坏、不支持、读取或写入失败 |

错误体和日志不得包含密码、哈希或完整请求体。

## 13. 管理员密码安全设计

### 13.1 唯一的管理员命令

统一入口新增一条跨平台命令：

```bash
pnpm yep setup-admin-password
```

Windows PowerShell 和 macOS shell 只负责转发到同一个 Node 管理入口。该入口新增内部 CLI 选项 `--setup-admin-password`，但不接受密码值作为参数，避免进入 shell 历史、进程列表和自动化日志。用户不需要区分开发、生产或自定义 Profile。

交互流程：

1. 显示固定目标 `~/.yep-anywhere/admin.json` 的绝对路径，但不显示任何密码信息。
2. 隐藏输入新管理员密码。
3. 隐藏输入确认密码。
4. 若文件已存在，明确提示此次操作会重置整个项目共用的管理员密码。
5. 原子写入 bcrypt 哈希并重新读取验证文件结构。
6. 显示一次安全提醒：“请妥善保存管理员密码；本项目不保存可找回的明文密码。”
7. 以成功或非零失败状态立即退出，不启动 HTTP 服务。

管理员密码的具体值不在前端、项目配置文件、源代码或环境变量中预置。

管理员密码和普通登录密码都沿用项目现有的至少 6 个字符规则，不强制字符组合，也不增加密码强度计。

### 13.2 文件权限

`admin.json` 和各 Profile 的 `auth.json` 都位于当前系统用户的数据目录，不得复制到静态资源、Bundle 示例配置或前端可访问目录。

- 继续复用现有 `OWNER_READ_WRITE_FILE_MODE` 与 `enforceOwnerReadWriteFilePermissions`，在 POSIX 上保持文件模式 `0600`。
- 本阶段不新增 Windows ACL 重写框架；沿用现有当前用户数据目录和文件权限行为。
- 写入时在目标目录创建只包含序列化哈希或认证状态的临时文件，刷新并以同文件系统原子替换目标文件；明文密码不得落盘。
- 写入或验证失败时保留旧文件并返回 `AUTH_CONFIG_ERROR`。
- 本阶段不引入跨进程文件锁。全局管理员服务按需读取 `admin.json`；单个服务进程内继续串行化 `auth.json` 写入。

### 13.3 网络提交限制

管理员密码只允许通过第 12.1 节定义的真实回环请求提交。远程 HTTP、HTTPS、可信代理、Tailscale 和桌面内部通道均不在管理员操作白名单中。

远程连接只能查看普通密码启用状态并使用普通密码登录；所有含管理员密码的登录或变更路径返回 `AUTH_LOCAL_REQUIRED`。后端不得仅凭任意客户端可伪造的请求头判断连接安全。

请求体、访问日志、错误日志和遥测不得记录管理员密码或登录密码。管理员密码验证失败可以记录时间、来源和错误类型，但不记录提交内容。

按本次需求，不为普通密码或管理员密码验证新增失败次数限制、延迟、锁定或验证码。管理员变更操作的安全性由独立密码、本机操作系统访问权、私有哈希文件和真实回环限制共同保证。

## 14. 管理员密码遗忘与恢复

系统不保存管理员密码提示、密保答案、明文副本或可逆密文。管理员遗忘密码时，以能够登录服务器本机操作系统并运行项目命令作为最高恢复权限。

设置和恢复都使用同一条命令：

```bash
pnpm yep setup-admin-password
```

恢复流程：

1. 在服务器本机运行命令。
2. 确认显示的是 `~/.yep-anywhere/admin.json` 的绝对路径。
3. 输入并确认新的管理员密码，不需要旧管理员密码。
4. 命令原子替换全局管理员哈希并立即退出。
5. 在任一 Profile 的本机回环登录页使用新管理员密码进入应用，再在“设置 → 本地访问”中修改或关闭忘记的普通登录密码。

管理员服务每次验证都读取全局文件，因此不需要停止、重启或重新构建开发/生产服务。管理员密码重置不修改任何 Profile 的普通密码、认证状态或 sessions。错误或成功信息不得回显新密码。

前端固定显示恢复说明：“管理员密码仅通过服务器本机命令配置。若忘记管理员密码，请在项目目录运行 `pnpm yep setup-admin-password`。”

## 15. 错误处理

### 15.1 服务管理错误

- 缺少 Node、pnpm、PowerShell、Bundle 或运行依赖时，指出具体缺项和修复建议。
- 端口被未知进程占用时拒绝误杀，显示端口、PID 和进程名。
- 启动后等待健康检查，超时显示运行模式、端口和日志路径并返回非零退出码。
- 停止后验证进程树和端口；仍有残留时明确报告，不虚报成功。
- 自启动配置缺失、损坏或动作路径失效时，`status` 显示“配置异常”，`enable-autostart` 负责幂等修复。
- 所有失败使用非零退出码，便于脚本和 CI 判断。

### 15.2 认证错误

- 远程普通密码错误显示“登录密码错误”；本机双路径登录失败显示“登录密码或管理员密码错误”。
- 管理员密码错误显示“管理员密码错误”。
- 管理员密码未配置时显示唯一命令 `pnpm yep setup-admin-password`。
- 非回环连接发起管理员操作时明确显示“只允许服务器本机管理”，不建议用 HTTPS 或代理绕过。
- `admin.json` 或 `auth.json` 无法解析、版本不支持、字段不完整、读取或写入失败时采用安全失败：不得自动关闭认证、清空密码或覆盖旧文件。
- 后端记录足以定位文件和状态的问题，但不记录密码、哈希或完整请求体。

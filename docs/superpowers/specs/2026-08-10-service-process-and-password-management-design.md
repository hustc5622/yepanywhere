# Yep Anywhere 跨平台服务进程与密码管理设计

- 日期：2026-08-10
- 状态：需求与设计已确认，待编写实施计划
- 适用平台：Windows、macOS
- 设计原则：复用现有实现、最少改动、平台原生守护、前后端职责清晰

## 1. 背景

项目已经具备开发模式、生产 Bundle、macOS LaunchAgent、Windows PowerShell 和计划任务脚本，以及基于 `auth.json` 的登录密码功能。但现有能力存在以下缺口：

- Windows 下部分启动路径仍依赖当前终端，关闭终端后服务可能退出。
- Windows 计划任务未安装时不会开机或登录自启动，且人工启动与自启动存在不同生命周期路径。
- macOS 与 Windows 的服务管理命令、菜单和自启动语义不完全一致。
- 根目录 `yep.mjs` 同时承担系统选择、菜单和部分业务逻辑，不符合“只做双端入口分发”的目标。
- 服务管理脚本的用户可见交互未完全中文化。
- 登录密码管理目前混在“本地访问”设置中，且缺少独立管理员密码验证。
- 现有 `auth.json` 只有登录密码，关闭认证时会丢弃密码，不能满足关闭后直接重新启用的要求。
- 管理员密码缺少安全配置、遗忘恢复和文件权限设计。

本设计补齐以上能力，同时保持未被本需求涉及的现有行为不变。

## 2. 目标

### 2.1 服务进程目标

1. 开发模式和生产模式均可后台静默运行，不受启动终端关闭影响。
2. Windows 与 macOS 均可启动、停止、重启开发和生产模式。
3. 生产模式可启用、关闭和查看登录桌面后的自动启动状态。
4. 生产模式可一键重新构建、重启并验证。
5. Windows 与 macOS 共用一个入口脚本，由入口自动识别系统并分发。
6. 服务脚本自身的菜单、提示、状态、帮助和错误均使用中文。
7. 开发模式与生产模式使用不同端口和数据 Profile，可以同时运行且互不误操作。

### 2.2 密码管理目标

1. 在前端“设置”中新增独立的“密码管理”子功能，与“外观”“模型”等标签保持相同导航逻辑。
2. 前端只管理登录密码，不设置、修改、显示或找回管理员密码。
3. 查看登录密码是否已设置、是否已启用不需要管理员密码。
4. 首次设置、启用、关闭和修改登录密码必须验证管理员密码。
5. 修改登录密码不要求输入原登录密码；输入管理员密码后即可设置新登录密码。
6. 登录密码或管理员密码错误时必须有明确提示。
7. 不增加登录失败次数限制、延迟、锁定或验证码。
8. 所有登录密码状态变更必须正确处理已有登录会话。
9. 管理员密码只通过服务器本机的后端交互命令配置和恢复，并得到安全存储。

## 3. 非目标

本次不包含：

- Windows Service 或 NSSM 等第三方服务包装器。
- 开发模式开机自启动。
- 系统启动后、用户登录前的系统级服务。本次 Windows 与现有 macOS 行为一致，采用用户登录后自动启动。
- Linux 服务管理能力扩展；保持项目现有 Linux 行为。
- 用户、角色、多管理员或权限分级系统。
- 前端管理员密码管理、管理员密码提示问题、邮件找回或网络恢复接口。
- 管理员密码明文、可逆密文或密码提示内容存储。
- 登录失败限制、验证码、账户锁定或登录退避策略。
- 复杂生产版本回滚系统。
- 构建系统重写及无关代码重构。

## 4. 总体方案与取舍

### 4.1 采用混合式平台原生方案

采用以下职责划分：

```text
yep.mjs（统一入口，只识别系统和转发参数）
├─ Windows → scripts/yep.ps1 → PowerShell + Task Scheduler
└─ macOS   → yep.sh          → shell + launchd
```

选择理由：

- Node.js 适合提供稳定、跨平台的统一入口，但不重复实现系统服务管理。
- Windows PowerShell 能直接管理计划任务、进程、ACL 和隐藏窗口。
- macOS shell 能直接管理 launchd、进程、权限和日志。
- 生产服务交给操作系统原生管理器守护，比单纯 Node.js `detached` 子进程更容易查询、重启和自启动。
- 复用现有 `yep.mjs`、`scripts/yep.ps1`、计划任务脚本、`yep.sh` 和 LaunchAgent 脚本，避免引入新的服务框架。

未采用的方案：

- 全部使用 Node.js 管理进程：跨平台代码表面统一，但仍需分别对接 Task Scheduler 和 launchd，且 Windows 子进程、信号和进程树管理更容易产生边缘问题。
- Windows Service：可在登录前启动，但需要管理员权限、服务账户与额外安装/卸载模型，不符合当前用户级 macOS LaunchAgent 语义和最少改动要求。

### 4.2 子系统边界

- 统一入口只做平台分发，不包含菜单、端口、进程和认证逻辑。
- Windows PowerShell 和 macOS shell 各自负责本平台的菜单、命令和服务管理。
- 服务脚本不读取、校验或修改密码。
- 后端认证模块负责 `auth.json`、密码哈希、管理员校验和会话失效。
- 前端“密码管理”只调用认证 API，不直接访问后端文件。

## 5. 统一入口设计

### 5.1 入口职责

根目录 `yep.mjs` 只执行以下工作：

1. 读取 `process.platform`。
2. Windows 自动调用 `scripts/yep.ps1`。
3. macOS 自动调用 `yep.sh`。
4. 原样传递全部命令行参数。
5. 继承标准输入、输出和错误输出，保留交互菜单能力。
6. 将后端脚本退出码原样返回给调用者。
7. 对不支持的系统显示中文错误并返回非零退出码。

入口不再询问用户选择操作系统，也不维护独立菜单或平台命令映射。无参数运行时，入口分发到当前系统脚本，由该脚本显示中文菜单；带参数运行时直接执行相应命令。

项目现有 `pnpm yep` 等入口继续指向 `node yep.mjs`。

### 5.2 命令接口

为兼容人工操作和自动化，命令参数保留英文，用户可见名称和反馈使用中文：

| 命令 | 中文功能 |
| --- | --- |
| `start-dev` | 启动开发模式 |
| `stop-dev` | 停止开发模式 |
| `restart-dev` | 重启开发模式 |
| `start-prod` | 启动生产模式 |
| `stop-prod` | 停止生产模式 |
| `restart-prod` | 重启生产模式 |
| `stop` | 停止开发和生产模式 |
| `status` | 查看完整服务状态 |
| `rebuild` | 重构建并重启生产模式 |
| `enable-autostart` | 启用生产模式登录自启动 |
| `disable-autostart` | 关闭生产模式登录自启动 |
| `help` | 显示中文帮助 |

现有 macOS 专用命令如 `enable-launchd` 可作为兼容别名保留，但菜单和文档统一推荐跨平台命令。

可继续支持 `start-dev --fg` 作为显式前台开发方式；交互菜单与 `start-dev` 的默认行为始终是后台静默运行。

## 6. 服务状态模型与命令语义

开发运行、生产运行和生产自启动是三个相互独立的状态：

```text
开发模式：停止 / 运行
生产模式：停止 / 运行
生产自启动：关闭 / 启用 / 配置异常
```

状态独立意味着：

- 开发与生产可以同时运行。
- `stop-prod` 不改变自启动设置；若自启动仍启用，下次登录仍会启动生产服务。
- `disable-autostart` 不停止当前生产服务。
- `enable-autostart` 只配置下次登录启动，不隐式启动当前服务。
- `stop` 停止两种运行模式，但不改变自启动设置。
- `rebuild` 不影响开发模式或生产自启动设置。

### 6.1 幂等要求

- 已运行时再次启动：提示“服务已在运行”，不创建重复进程。
- 已停止时再次停止：提示“服务当前未运行”，命令正常结束。
- 已启用时再次启用自启动：检查并修复配置，不重复注册。
- 已关闭时再次关闭自启动：提示当前已经关闭。
- 重启等价于准确停止目标模式后再启动该模式。

### 6.2 状态输出

`status` 至少显示：

- 当前操作系统和服务管理器。
- 开发模式：运行状态、端口、PID、数据 Profile、日志路径。
- 生产模式：运行状态、端口、PID 或系统任务状态、数据 Profile、日志路径。
- 生产自启动：已启用、已关闭或配置异常。
- 计划任务或 LaunchAgent 的安装、加载、运行和最近结果。
- 发现端口占用、残留 PID 或管理器状态不一致时给出中文诊断。

## 7. Windows 设计

### 7.1 平台基线

- 兼容系统自带 Windows PowerShell 5.1，不强制要求 `pwsh`。
- 生产服务由 Task Scheduler 管理。
- 开发服务由独立隐藏 PowerShell 启动器管理。
- 所有工作目录、脚本路径、Node 路径和日志路径使用绝对路径。

### 7.2 生产模式生命周期

计划任务是生产模式唯一的生命周期入口。人工启动、重启、重构建后的启动和登录自启动都通过同一个任务定义执行，避免产生两套不同的后台进程。

计划任务设计：

- 使用现有稳定任务名称 `YepAnywhereServer`。
- 以当前用户身份运行，不保存用户密码，不要求管理员权限。
- 触发器为当前用户 `AtLogOn`，与 macOS LaunchAgent 的登录后启动语义一致。
- 隐藏运行 PowerShell 守护脚本，并重定向标准输出和错误输出。
- 禁止同一任务并行创建多个实例。
- 不设置执行时限。
- 关键进程失败时按合理间隔重新启动，并使用接近持续守护的高重试次数。

自启动状态与任务动作分离：

- 首次启动生产服务时可以按需创建可人工启动的任务定义。
- 启用自启动时，为任务启用或安装 `AtLogOn` 触发器。
- 关闭自启动时，只移除或禁用登录触发器，保留任务动作供人工启动。
- 关闭自启动不会停止当前任务实例。

现有 `scripts/install-task-scheduler.ps1`、`scripts/uninstall-task-scheduler.ps1` 和 `scripts/run-yepanywhere.ps1` 继续复用，但职责调整为上述语义。

### 7.3 生产守护脚本

`scripts/run-yepanywhere.ps1` 继续作为计划任务执行入口，负责：

1. 校验生产 Bundle 和运行依赖。
2. 设置生产环境变量、端口和数据目录。
3. 隐藏启动服务器及必要的桥接进程。
4. 将输出写入现有生产日志目录。
5. 等待并监控全部关键进程，而不只监控主服务器 PID。
6. 任一关键进程异常退出时清理同一生产实例的残留进程并以非零状态退出，让计划任务重新拉起完整实例。

正常执行 `stop-prod` 时先停止计划任务实例，再清理经身份确认的生产进程，防止守护策略立即重新启动服务。

### 7.4 开发模式后台运行

默认 `start-dev` 使用 `Start-Process` 创建独立于当前终端的隐藏 PowerShell 启动器。启动器设置明确的工作目录和开发 Profile，运行现有 `pnpm dev`，重定向输入输出，并记录父进程 PID 与日志位置。

关闭原终端后，隐藏启动器和开发进程树继续运行。开发模式不注册计划任务，也不承诺应用崩溃后的系统级自动重启；开发构建工具自身仍按现有方式管理其子进程。

### 7.5 Windows 进程识别

停止服务不能仅按端口结束进程。目标身份至少综合：

- 计划任务运行状态。
- PID 文件或已知启动器 PID。
- 进程命令行中的项目路径、Bundle 路径、Profile 和模式。
- 对应端口作为辅助验证。

若端口属于无法确认的其他程序，脚本拒绝结束该程序，并显示端口、PID、进程名称和处理建议。

## 8. macOS 设计

### 8.1 生产模式

继续复用现有 launchd/LaunchAgent 方案：

- 当前用户登录桌面后由 LaunchAgent 启动生产服务。
- 使用 `RunAtLoad` 和 `KeepAlive` 保持生产服务常驻。
- 人工启动和重启也通过 launchd 管理的同一生产定义执行。
- `enable-autostart` 安装下一次登录所需的 LaunchAgent 配置，但不额外启动当前生产服务。
- `disable-autostart` 取消下一次登录自动加载，但不停止当前正在运行的生产服务。
- `stop-prod` 停止当前生产实例，但不删除自启动配置。

若需要在关闭自启动后人工运行生产服务，`yep.sh` 仍使用同一份生产 LaunchAgent 定义在当前登录会话中加载；下一次登录因未安装自启动项而不会自动加载。

### 8.2 开发模式

继续复用现有 `nohup` 后台启动方式，并确保：

- 标准输入连接 `/dev/null`。
- 标准输出和错误输出写入开发日志。
- 保存可验证的 PID。
- 关闭终端不会发送导致开发进程退出的信号。

### 8.3 脚本一致性

`yep.sh` 增加或补齐 `stop-dev`、`stop-prod`、`disable-autostart` 等与 Windows 一致的命令和中文交互，但不重写现有 launchd 安装和生产构建流程。

## 9. 重构建生产模式

`rebuild` 继续沿用项目当前的完整生产 Bundle 流程：

1. 执行 `pnpm lint`。
2. 执行 `pnpm typecheck`。
3. 构建客户端。
4. 执行 `pnpm build:bundle`。
5. 在 `dist/npm-package` 中使用 `npm ci --omit=dev` 安装运行依赖，不使用 pnpm。
6. 验证 Bundle 完整性。
7. 构建成功后通过当前系统的生产服务管理器重启或启动生产服务。
8. 比较运行服务、前端和 Bundle 的 `buildId`，确认部署的是本次构建。

错误语义：

- 构建或验证失败时，不继续执行生产重启。
- 不主动停止构建前正在运行的生产进程。
- 明确显示失败阶段、退出码和日志路径。
- 本次不增加生产版本快照和自动回滚机制。

## 10. 前端密码管理入口

### 10.1 设置导航

在前端“设置”中新增“密码管理”标签，作为与“外观”“模型”“本地访问”等并列的设置分类。建议路由为 `/settings/password`，并复用现有设置分类、布局和响应式导航逻辑。

现有“本地访问”页面中的认证设置迁移到“密码管理”，该页面只保留网络访问、主机或本地连接相关设置。密码管理不得继续分散在两个设置标签中。

### 10.2 页面结构

页面保持简单，只包含：

1. 状态区域：显示“未设置”“已设置但未启用”或“已启用”。查看状态不需要管理员验证。
2. 操作区域：根据状态显示首次设置、启用、关闭和修改登录密码。
3. 安全说明：说明管理员密码只在服务器后端配置，前端仅临时用于身份验证。
4. 忘记管理员密码说明：提示登录服务器本机并运行管理员密码恢复命令。

管理员密码输入框只在用户发起变更操作时显示，不作为独立设置项，也不显示管理员密码是否已配置。

### 10.3 操作表单

- 首次设置：管理员密码、新登录密码、确认新登录密码。
- 启用登录密码：管理员密码。
- 关闭登录密码：管理员密码，并提供明确确认提示。
- 修改登录密码：管理员密码、新登录密码、确认新登录密码；不输入原登录密码。

页面复用现有表单、按钮、错误、成功和警告样式。请求进行中禁用重复提交；请求结束、离开页面或组件卸载时清空管理员密码输入。管理员密码不得写入 URL、日志、localStorage、sessionStorage、IndexedDB 或任何前端持久化状态。

### 10.4 登录页面

登录页面只负责登录，不再作为首次设置登录密码的主要入口。认证关闭时用户可以进入应用并从“设置—密码管理”完成首次设置。

登录密码错误显示明确的“登录密码错误”，不使用模糊的“登录失败”。连续错误不会触发次数限制、延迟、锁定或验证码。

## 11. 认证状态模型

### 11.1 `auth.json`

继续使用现有数据目录中的 `auth.json`，升级为能区分管理员密码和登录密码的状态。逻辑结构为：

```json
{
  "version": 2,
  "enabled": true,
  "admin": {
    "passwordHash": "bcrypt hash"
  },
  "account": {
    "passwordHash": "bcrypt hash"
  },
  "sessions": "沿用现有会话数据结构"
}
```

约束：

- `admin.passwordHash` 与 `account.passwordHash` 完全独立。
- 两种密码都只保存带随机盐的 bcrypt 哈希，沿用项目当前 bcrypt 成本参数。
- 管理员密码不存在时允许登录和只读状态查询，但拒绝所有登录密码变更。
- `account` 不存在表示尚未设置登录密码。
- `account` 存在且 `enabled=false` 表示登录密码已保存但认证当前关闭。
- 关闭认证不得删除 `account.passwordHash`。
- API 永远不返回任何密码哈希，也不返回管理员密码状态。

### 11.2 状态迁移

| 操作 | 认证结果 | 登录密码哈希 | 会话处理 | 前端结果 |
| --- | --- | --- | --- | --- |
| 首次设置 | 启用 | 新建 | 清除全部会话 | 清除 Cookie 并进入登录页 |
| 启用 | 启用 | 保留 | 清除全部会话 | 清除 Cookie 并进入登录页 |
| 关闭 | 关闭 | 保留 | 清除全部会话 | 清除 Cookie，继续使用应用 |
| 修改（已启用） | 保持启用 | 替换 | 清除全部会话 | 清除 Cookie 并进入登录页 |
| 修改（已关闭） | 保持关闭 | 替换 | 清除全部会话 | 显示成功并停留在设置页 |

所有登录密码状态修改都必须先验证管理员密码。现有登录会话 Cookie 不能替代管理员密码验证。

### 11.3 旧数据迁移

读取旧版 `auth.json` 时自动迁移：

- 保留现有 `enabled`、登录密码哈希和会话结构。
- 管理员密码初始为空。
- 登录和状态查询继续工作。
- 登录密码修改接口返回“管理员密码尚未在服务器后端配置”。
- 用户通过本机后端命令配置管理员密码后，才能在前端修改登录密码状态。

首次新增管理员密码不改变现有登录密码和会话；替换或恢复已有管理员密码时清除全部登录会话。

## 12. 密码 API 设计

继续复用现有 `/api/auth` 路由和认证服务，只调整请求验证与状态转换：

| API | 权限与用途 |
| --- | --- |
| `GET /api/auth/status` | 无需管理员密码；只返回登录密码是否已设置、是否已启用 |
| `POST /api/auth/setup` | 管理员密码 + 新登录密码；首次设置并启用 |
| `POST /api/auth/enable` | 管理员密码；重新启用已保存的登录密码 |
| `POST /api/auth/disable` | 管理员密码；关闭认证但保留登录密码哈希 |
| `POST /api/auth/change-password` | 管理员密码 + 新登录密码；替换登录密码 |
| `POST /api/auth/login` | 登录密码；建立现有登录会话 |
| `POST /api/auth/logout` | 注销当前登录会话 |

若需要兼容现有旧路由或字段，兼容层最终仍必须进入相同的管理员验证和状态转换，不允许保留绕过管理员验证的网络接口。

现有后端本机命令也不能成为登录密码修改的绕过路径：

- 保留 `--setup-auth` 命令名，但不再接受明文密码命令行参数；改为隐藏输入管理员密码和新登录密码，并执行与前端相同的会话失效语义。
- 保留 `--auth-disable` 命令名，但执行前隐藏输入并验证管理员密码。
- 两个命令都不得设置、替换或恢复管理员密码；管理员恢复只能使用专用的 `--setup-admin-password`。

后端返回稳定错误码，前端映射为本地化提示。至少区分：

- 管理员密码未配置。
- 管理员密码错误。
- 登录密码错误。
- 登录密码尚未设置。
- 当前连接不允许提交管理员密码。
- 密码格式不符合现有规则。
- 认证配置损坏或写入失败。

## 13. 管理员密码安全设计

### 13.1 后端本机配置

新增后端 CLI 选项 `--setup-admin-password`，通过源代码后端入口或生产 Bundle CLI 在服务器本机执行。该命令不得接受密码值作为命令行参数，避免进入 shell 历史、进程列表和自动化日志。

交互流程：

1. 解析目标 Profile 或 `YEP_ANYWHERE_DATA_DIR`。
2. 显示目标环境和 `auth.json` 绝对路径，但不显示任何密码信息。
3. 隐藏输入新管理员密码。
4. 隐藏输入确认密码。
5. 如果已有管理员密码，明确提示此次操作是恢复或替换。
6. 写入 bcrypt 哈希并验证写入结果。
7. 显示一次安全提醒：“请将管理员密码保存到可信的密码管理器；本项目不保存可找回的明文密码。”

管理员密码的具体值不在前端、项目配置文件、源代码或环境变量中预置。

管理员密码最少 12 个字符，不强制特定字符组合；登录密码继续采用项目现有后端长度规则。前端只镜像后端规则和错误提示，不维护不同的第二套校验阈值。

### 13.2 文件权限

`auth.json` 位于运行数据目录，不得复制到静态资源、Bundle 示例配置或前端可访问目录。

- macOS/POSIX：文件权限保持为 `0600`，目录只允许当前用户访问。
- Windows：写入后设置并验证 ACL，移除 `Everyone`、`Users`、`Authenticated Users` 等宽泛主体的继承访问，只保留当前运行用户以及操作系统所需的受信任主体。
- 每次创建、迁移、修改和恢复后都重新校验权限。
- 文件采用临时文件写入、设置权限、刷新并原子替换，避免留下部分 JSON 或包含明文密码的临时文件。

### 13.3 网络提交限制

管理员密码只允许通过以下连接提交：

- 回环地址访问。
- 直接 HTTPS。
- 项目已有可信代理机制确认的 HTTPS。
- 受信任桌面内部通道。

普通局域网 HTTP 连接只能查看登录密码状态，所有变更操作返回明确的安全错误。后端不得仅凭任意客户端可伪造的转发头判断连接安全。

请求体、访问日志、错误日志和遥测不得记录管理员密码或登录密码。管理员密码验证失败可以记录时间、来源和错误类型，但不记录提交内容。

按本次需求，不为登录密码或管理员密码验证新增失败次数限制、延迟、锁定或验证码。管理员变更操作的安全性由独立强密码、本机配置、受限文件权限和安全传输共同保证。

## 14. 管理员密码遗忘与恢复

系统不保存管理员密码提示、密保答案、明文副本或可逆密文。管理员遗忘密码时，以能够登录服务器本机操作系统并访问数据目录作为最高恢复权限。

恢复仍使用 `--setup-admin-password`：

1. 通过统一服务脚本停止使用目标 `auth.json` 的开发或生产实例，避免并发写入。
2. 在服务器本机运行后端管理员密码设置命令。
3. 确认命令显示的 Profile 和绝对数据路径正确。
4. 输入并确认新的管理员密码，不需要旧管理员密码。
5. 原子更新 `admin.passwordHash`，不修改登录密码和认证启用状态。
6. 清除全部登录会话，防止恢复期间已有会话继续保留。
7. 恢复原先需要运行的服务并检查状态。

默认数据位置：

- 生产：`~/.yep-anywhere/auth.json`
- 开发：`~/.yep-anywhere-dev/auth.json`
- 自定义：由 `YEP_ANYWHERE_DATA_DIR` 指定

若服务仍在运行或无法取得安全写入条件，恢复命令拒绝写入并提示先停止对应服务。错误或成功信息不得回显新密码。

前端固定显示恢复说明：“管理员密码仅在服务器后端配置。若忘记密码，请登录服务器本机并运行管理员密码恢复命令。”管理员密码验证错误时同时提供该说明的入口。

## 15. 错误处理

### 15.1 服务管理错误

- 缺少 Node、pnpm、PowerShell、Bundle 或运行依赖时，指出具体缺项和修复建议。
- 端口被未知进程占用时拒绝误杀，显示端口、PID 和进程名。
- 启动后等待健康检查，超时显示运行模式、端口和日志路径并返回非零退出码。
- 停止后验证进程树和端口；仍有残留时明确报告，不虚报成功。
- 自启动配置缺失、损坏或动作路径失效时，`status` 显示“配置异常”，`enable-autostart` 负责幂等修复。
- 所有失败使用非零退出码，便于脚本和 CI 判断。

### 15.2 认证错误

- 登录密码错误显示“登录密码错误”。
- 管理员密码错误显示“管理员密码错误”。
- 管理员密码未配置显示后端配置和恢复指引。
- 不安全连接显示禁止原因和 HTTPS/本机操作建议。
- `auth.json` 无法解析、字段不完整或写入失败时采用安全失败：不得自动关闭认证或清空密码。
- 后端记录足以定位文件和状态的问题，但不记录密码、哈希或完整请求体。

### 16.2 Windows 人工验收

### 16.4 密码管理验收

1. 无需管理员密码即可查看登录密码配置和启用状态。

5. 关闭认证后继续访问应用，登录密码哈希保留。
6. 重新启用后旧会话失效，原登录密码仍可使用。

8. 普通局域网 HTTP 可查看状态但不能提交管理员密码。
9. 忘记管理员密码时，可在本机恢复管理员密码，登录密码保持不变且旧会话失效。
10. `auth.json`、日志、浏览器存储和命令行历史中不存在明文密码。

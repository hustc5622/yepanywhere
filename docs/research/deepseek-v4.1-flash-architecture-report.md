## 0. 一句话总结

> V4.1 Flash 的思路是**「把记忆和推理分家」**：死记硬背的知识塞进一张约 1966 亿参数的查表（Engram，几乎不耗算力），现场推理交给 Transformer；同时把网络拆成「读题用 8B、动笔用 16B」的非对称结构（CED）；注意力改成跨层共享一份高分辨率记忆、只精读最相关的 512 个位置。结果是参数从 284B 涨到 552B，生成速度反而快了约 3 倍（120 → 361 tok/s），LLM 耗时下降约 69%。

| 项 | DeepSeek V4.1 Flash | DeepSeek V4 Flash |
| --- | --- | --- |
| 总参数量 | **552B**（其中约 **196.6B** 来自 Engram 查表 🟡） | 284B |
| 激活机制 | **非对称激活（全新架构 CED）** | 对称激活（传统 MoE） |
| 输入（prefill）激活 | **8B** | 13B |
| 输出（decode）激活 | **16B** | 13B |

## 1. 前置概念：理解本篇需要的 4 个基础

### 1.1 prefill 与 decode：读题 vs 动笔

模型是一个 token 一个 token 往外算的，但要拆成两个阶段：

- **prefill（读题）**：把用户输入的几万到上百万 token **一次性并行**读进去。**算力密集**，像一次把整本书翻完。
- **decode（动笔）**：逐个 token 生成，每吐一个字都要回头查全部历史。**显存带宽密集**，瓶颈不在算力而在「翻笔记」的速度。

**这个区分是本篇的关键**：V4.1 的核心设计就是**读题用便宜的配置，动笔用贵的配置**。

### 1.2 KV Cache：模型贴在书上的便签

每读一个 token，模型会生成两份内部记录：**K（Key，索引）**和 **V（Value，内容）**。为避免生成新词时重算全部历史，这些 K/V 会被缓存下来，即 **KV Cache**。

- **类比**：读 500 页的书，每读完一页贴一张便签，之后引用直接翻便签。
- **代价**：书越厚便签越多。100 万 token 上下文的 KV Cache 可达数百 GB——**这是长上下文最贵的地方**。

### 1.3 MoE：专家会诊

**MoE（Mixture of Experts，混合专家）**：模型内含多组「专家」，每个 token 只挑其中少数几个参与计算。

这解释了「总参数 284B、激活只有 13B」的现象——**参数总量 ≠ 每 token 计算量**。

### 1.4 注意力的平方成本与稀疏注意力

标准 attention 要计算「当前 token × 历史上每个 token」的相关度，历史翻倍则计算量翻 4 倍（O(n²)）。**稀疏注意力**的做法是只跟最相关的少数位置计算。

- **类比**：要查「这个函数在哪定义过」，笨办法是逐行读完 100 万行；聪明办法是先定位相关文件，再只精读那几行。
- **V4.1 的技术点三，本质上是把这套「图书馆检索流程」做进了网络内部。**

## 2. 技术点一：CED —— 把网络拆成「理解层」和「生成层」

### 2.1 是什么

**CED = Causal Encoder–Decoder（因果编码器-解码器）**。「因果」指每个 token 只能看到自己左侧的历史。

原文（引用官方 config）✅：

> CED 下 decode 每 token 激活 16B，prefill 只激活 8B。

拆法：

- **下半层当 Encoder（编码器）**：只在 prefill 阶段干活，把上下文压缩成紧凑表示。
- **上半层当 Decoder（解码器）**：decode 时主要跑这一半；全局 KV 直接从 Encoder 最后一层的 hidden state **投影**过来，不必自己重建一套。

### 2.2 为什么这么设计

举例：让 agent 读一个 100 万 token 的代码仓库，只回答「这个 bug 在第几行」（输出可能 20 个 token）。

| 方案 | 读题（100 万 token） | 动笔（20 token） | 结果 |
| --- | --- | --- | --- |
| 传统对称架构 | 13B 全量 | 13B 全量 × 20 次 | 贵的部分被浪费在「写」这个动作上 |
| V4.1 CED | **8B 编码器** | **16B 解码器 × 20 次** | 读便宜、写贵但只贵 20 次 |

原文的总结：**「Agent 这种『读很长、写不那么长』的场景下，prefill 应该会更便宜一些。」**

### 2.3 附带好处：上下文更紧凑

Decoder 各层不需要各自从自己的 hidden state 构造一套 global KV，而是**共用 Encoder 末层投影出的那一份**——等于**多层的便签合并成一份**，KV Cache 直接变小。

## 3. 技术点二：Engram —— 把「背诵」从神经网络里搬出来

### 3.1 核心思想

**把模型能力拆成两部分：**

| 内容类型 | 交给谁 |
| --- | --- |
| 需要推理的东西（逻辑、计算、推理链） | Transformer（神经网络，GPU 上算） |
| 需要大量记忆、但计算价值不高的东西（固定搭配、实体名、专有名词、惯用语） | **N-gram 哈希查表（Engram）** |

- **类比**：一个中文很好的外国人。语法和逻辑靠脑子现场推（Transformer）；但「北京烤鸭」「特朗普」「Hello World」这类固定搭配是**背下来的**，不必现场推——**Engram 就是给模型加的一本背诵手册**。

### 3.2 术语逐个拆解

**① N-gram = 连续的 n 个 token**

输入 `我 爱 吃 北京 烤鸭`：

- 1-gram：`我`、`爱`、`吃`、`北京`、`烤鸭`
- 2-gram：`我爱`、`爱吃`、`吃北京`、`北京烤鸭`
- 4-gram：`我爱吃北京` …

V4.1 配置为**最高 4-gram**，即最多记住 4 个连续 token 的固定搭配 ✅。

**② 哈希（Hash）= 把任意内容映射成固定范围内的编号**

像图书馆的**书架编号规则**：不必给每本书编详细目录，按规则算出编号就能定位。

- **好处**：不需要存储原始字符串，**O(1) 常数时间**查表，内容重复率越高越省。
- **③ 哈希冲突**：不同内容算出同一编号即「撞车」。V4.1 用 **8 个哈希头（Hash heads）**，即**8 套不同编号规则各查一次再融合**，用多个视角把撞车概率压下去。
- **④ Embedding**：每个槽位存一个 **256 维向量**（256 个浮点数），代表该 n-gram 的语义。
- **⑤ Hash vocab 16M**：每套哈希规则的槽位数是 1600 万（16,777,216）。

### 3.3 具体配置

| 项 | V4.1 Flash | 来源 |
| --- | --- | --- |
| Engram 插入层 | **第 1 层、第 14 层** | ✅ 官方 config |
| 两张 Engram 表 | **384,006,168 行 + 384,016,682 行** | ✅ |
| 每条 embedding | **256 维** | ✅ |
| N-gram 长度 | **最高 4-gram** | ✅ |
| Hash heads | **8** | ✅ |
| Hash vocab | **16M** | ✅ |
| 合计参数量 | `(384,006,168 + 384,016,682) × 256 ≈ 196.61B` | 🟡 社区按公式反推 |

> **本项目补充观察** 🔵：两张表行数几乎相同但差约 1 万行（384,006,168 vs 384,016,682），推测分别对应**两个插入层各自的槽位表**；此对应关系为推测，非原文明确说明。

### 3.4 为什么说这是「聪明的参数增长」

**关键点：查表几乎不花 FLOPs。**

- 传统堆参数：每个 token 都要过矩阵乘法 → 直接吃 GPU 算力。
- Engram 堆参数：只是**读几行内存** → 吃的是**内存容量与带宽**。

原文结论口径：**「V4.1 的参数增长方式可以理解成：增加大量『存储容量』，少增加『每 Token 动态计算量』。」**

以及硬件层面的推论（原文认为最有价值的一点）：

> 以后大模型参数增长也不一定继续全部买 GPU FLOPs，**相当一部分参数可以变成「CPU/DRAM 上的大型可寻址记忆」**。

即**扩容从「堆显卡」部分转向「堆内存条」**。同时支持**异步 prefetch**：地址可提前计算，内存搬运与计算重叠，不阻塞主流程。

### 3.5 与 Qwen3.8-Flash-Next 的对比

| DeepSeek Engram | Qwen3.8 N-gram Embedding |
| --- | --- |
| 根据局部 N-gram 计算确定性地址 | 根据局部 N-gram 查 embedding |
| 巨大查找表 | 巨大查找表 |
| 参数很多，但每 Token 只读很少几行 | 同样 |
| 可以放 Host Memory | 同样可以放 Host Memory |
| 可提前算地址做异步 prefetch | Qwen 也明确这么做 |
| 用很少 FLOPs 扩模型容量 | 同样目标 |

原文认为 DeepSeek 的 Engram 是**更完整的「Conditional Memory（条件记忆）」模块设计**，且规模远大于 Qwen3.8 的 51B N-gram Embedding（约 196.6B vs 51B，接近 4 倍）；Qwen 方面也承认受到 DeepSeek Engram 的启发。

## 4. 技术点三：注意力机制重构

### 4.1 V4 老方案：CSA 与 HCA 交替

V4 Flash 0731 的 `compress_ratio` 为 **4, 128, 4, 128 …**：

- **CSA（约 4 倍压缩）**：把若干 token 压成一个表示，再做稀疏检索。
- **HCA（128 倍压缩）**：直接做 128 倍压缩，在被压扁的序列上做 attention。

- **类比**：CSA 是「每 4 页做一张摘要」，HCA 是「每 128 页做一页摘要」。HCA 最省，但**信息丢失严重**——128 倍压缩后具体某一行代码早已糊掉。

### 4.2 V4.1 新方案：高分辨率 KV + 分层检索

主干压缩率从 `4, 128` 变为 **`2, 2, 2 … 1, 1, 1 …`**：

- **ratio=2**：两个 token 池化成一个 KV
- **ratio=1**：**完全不做时间维压缩**

方向性转变：V4 是「存得少、算得多」，V4.1 是**「存得更细（高分辨率），靠别的地方省计算」**。

省计算的两招：

**① 跨层共享 KV**

原文口径：通过降低时间维压缩率提高每份 KV 的信息量，同时**降低「每层重复保存、重复搜索历史」的浪费**——历史表示保存得更细，但一组层共享同一份长程记忆。

- **类比**：以前的会议记录是**每个部门各记一份、各自摘要**；现在是**一份高清完整纪要，全公司共享**。纪要更详细，但只存一份。

**② 分级检索（两级）**

- 一级：**block candidate retrieval（块级候选检索）**——粗筛
- 二级：**position-level top-512 retrieval（位置级 top-512 检索）**——细选

配合 **128 token 本地 Sliding Window（滑动窗口）** 与**远程 compressed KV memory**，最后才执行 sparse attention。

**完整链路（原文的图书馆比喻）**：

1. **粗筛**：哪些文件、哪些代码区域大概和当前问题相关？→ 得到 **Shared Candidate Pool（共享候选池）**
2. **细选**：在候选范围里精确挑出 **top-512 个位置**
3. **精算**：只把这 512 个位置送进 sparse attention

**关键细节**：**共享候选集，但不共享最终 Top-512**——粗筛结果共用（省掉重复的全库搜索），但精挑细选由各层自己做（保留层间差异化判断）。

### 4.3 三种模式：Full / Reindex / Reuse

**不是每层都必须重新搜一遍**：

| 模式 | Main KV | Indexer K | Top-512 | 工作量 |
| --- | --- | --- | --- | --- |
| **Full Mode** | 新生成 | 新生成 | 新搜索 | **最大** |
| **Reindex Mode** | 复用 | 复用 | 重新搜索 | **中等** |
| **Reuse Mode** | 复用 | 不跑 Indexer | 直接复用 | **最小** |

**原文给的具体走位（100 万 token 代码库场景）**：

| 层 | 动作 | 模式 |
| --- | --- | --- |
| 第 20 层 | 做一次成本较高的全库搜索：「哪些文件、哪些代码区域大概和当前问题相关？」→ 得到 Shared Candidate Pool | Full |
| 第 24 层 | 语义理解更深后：「在刚才那批候选代码里重新选 512 个位置」 | Reindex |
| 第 25~27 层 | 没必要重复搜索，直接沿用上层结果 | Reuse |

### 4.4 整体演进公式

> V4 的 `4× CSA + 128× HCA 交替结构`，在 V4.1 中变成 **`1×/2× 高分辨率 KV` + `跨层 KV 共享` + `跨层 Index 共享` + `两级候选检索` + `top-512 Sparse Attention`** 的组合。

### 4.5 官方架构图的文字描述

据官方架构图（截图）：

- **Encoder 列（从左下到右上）**：`Engram + Text Embedding + Vision Embedding`（视觉侧另有 `Vision Encoder`）→ **`Single-Pass mHC`** 融合 → `Embedding` → `MoE + SWA`（滑动窗口，局部）×2 → `MoE + CSA2(2, Full)`（全局检索）→ `MoE + CSA2(2, Reuse)`（分组复用，图中标 ×3 / ×5）→ 输出 `Enc. Hidden States`。
- **Decoder 列**：以 `Main KV` 作为输入（与 Encoder 之间标有 `CED` 连接）→ `MoE + CSA2(1, Full)` → 向上依次是 `MoE + CSA2(1, Reuse)`（×3）、`MoE + CSA2(1, Reindex)`（×4）→ 顶部 `DSpark` 输出头。
- **右侧索引支路**：`Hierarchical Sparse Indexer` → `Candidate Pool` → 回灌到 `CSA2(1, Reindex)` 层。

🔵 图中 `Single-Pass mHC` 从命名看是「单次前向的多头融合/压缩」，把 Engram、文本、视觉三路输入一次融合；此为字面推测，未经官方说明确认。

同期发布的 **DeepSeek Harness v0.1.5** 官方公告（截图原文）：

> This release is deeply integrated with the training of the DeepSeek V4.1 Flash model, **with the model specifically trained and optimized for different configurations within DeepSeek Harness.**

含义：模型与 agent 框架（系统提示、工具调用格式、上下文管理策略）**一起长出来**。好处是开箱即用的 agent 体验更好；代价见第 7 节。

## 6. 效果数据

🟡 社区实测对比（V4.1 Flash vs V4 Flash Vision Exp）：

| 指标 | V4.1 Flash | V4 Flash Vision Exp | 变化 |
| --- | --- | --- | --- |
| 总耗时 | **18m 49s** | 30m 11s | −38% |
| 总 Token 使用量 | **11.59M** | 20.31M | −43% |
| 输出 Token | **126K** | 154K | −18% |
| LLM 时间 | **7m 48s** | 25m 10s | **−69%** |
| 生成速度 | **361 Token/s** | 120 Token/s | **≈3×** |
| Cache Hit | 99.5% | 99.7% | 基本持平 |

**解读**：

1. **LLM 时间降 69%，总耗时只降 38%** → 剩余时间花在工具调用、文件 IO、Harness 调度上，**模型已不是瓶颈**。
2. **总 token 降 43%** → 不只更快，还更「省话」，agent 场景直接省成本。
3. **两个版本 Cache Hit 都是 99%+** → **提速不是靠缓存优化**（V4.1 命中率还略低），而是架构本身带来的。
4. 社区实测普遍 **300~400 tok/s，很多在 350 tok/s 以上**。

## 7. 收益与需要观察的点

### 7.1 收益

1. **速度**：约 3 倍，且不是缓存或服务端优化堆出来的。
2. **成本结构改变**：参数增长从「买 GPU 算力」部分转为「买内存容量」，边际扩容成本显著下降。
3. **长上下文变便宜**：KV 跨层共享 + 高压缩率 + 稀疏检索，三层叠加压缩 100 万 token 场景的 KV 规模。
4. **与 agent 负载精确匹配**：读多写少的工作负载，正好对上 CED 的 8B/16B 非对称设计。

### 7.2 需要观察的点 🔵（本文作者判断）

1. **Engram 的天花板在「重复率」**：查表对固定搭配、常见实体极高效，但**新颖表达、长尾知识、首次出现的内容**帮不上忙，仍需 Transformer 硬推。收益大小取决于负载中「套路化内容」的占比——agent 场景套路多，收益大；写小说、做数学证明类负载收益有限。
2. **FLOPs 省了，内存带宽成新瓶颈**：查表不花算力但**要读内存**。表若放在 CPU/DRAM 还要过 PCIe。异步 prefetch 正是在缓解该问题，但能否完全掩盖需看实际吞吐。
3. **KV 跨层共享可能损失层间差异**：不同深度层的注意力需求本来不同。V4.1 用 CSA2 的 Full/Reindex/Reuse 三种模式补偿——**这本身说明「不能全共享，必须留几层重新搜」**。
4. **与 Harness 深度耦合是双刃剑**：开箱即用体验更好，但换框架、换提示词体系、自建 agent 时，**可能拿不到官方宣传中的效果**。
5. **数字来源需注意**：本报告所有具体数值均来自社区解读与实测，**非官方报告原文**；尤其「552B 中 196.6B 是 Engram」是社区用 config 反推，官方口径可能不同。

## 8. 名词速查表

| 术语 | 一句话解释 |
| --- | --- |
| **prefill** | 读题阶段，一次性并行处理全部输入，算力密集 |
| **decode** | 动笔阶段，逐个 token 生成，带宽密集 |
| **KV Cache** | 缓存的索引（K）与内容（V），相当于读书记的便签 |
| **MoE** | 混合专家，每个 token 只激活少数专家 |
| **CED** | 因果编码器-解码器，把网络拆成理解层与生成层，非对称激活 |
| **Engram** | 条件记忆模块，用 N-gram 哈希查表替代死记硬背 |
| **N-gram** | 连续的 n 个 token，如 2-gram =「北京烤鸭」 |
| **Hash** | 把内容映射成固定编号，O(1) 定位 |
| **Hash heads** | 多套哈希规则并行，降低冲突 |
| **FLOPs** | 浮点运算次数，衡量算力消耗 |
| **Host Memory** | 主机内存（CPU 侧 DRAM），比显存便宜得多 |
| **Prefetch** | 提前搬运数据，与计算重叠 |
| **CSA / HCA** | V4 的两种压缩注意力（约 4 倍 / 128 倍压缩） |
| **CSA2** | V4.1 的压缩注意力，含 Full / Reindex / Reuse 三种模式 |
| **SWA** | Sliding Window Attention，只看最近 N 个 token 的局部注意力 |
| **Top-k / Top-512** | 只挑相关度最高的 k 个位置参与计算 |
| **Sparse Attention** | 稀疏注意力，不算全部历史，只算最相关的 |
| **Harness** | agent 运行时框架（系统提示、工具调用、上下文管理） |
| **Candidate Pool** | 共享候选池，一级粗筛产出的候选位置集合 |

| 位置 | 内容 |
| --- | --- |

**与本项目的相关性**：本仓库定位是「移动端优先的 coding agent 监督器」，主要负载正是**读多写少的 agent 场景**——恰好是 CED 非对称设计与 Engram 条件记忆受益最大的场景。因此 V4.1 Flash 的「快」不完全是通用意义上的快，而是**与本仓库典型负载高度同构的快**；评估实际体验时，应使用真实的长上下文 agent 会话而非短问答做基准。
